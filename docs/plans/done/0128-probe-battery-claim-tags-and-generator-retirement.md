## Goal

Give every load-bearing assertion an identity that is **declared by its author, lives on the assert's own last line as a trailing `# claim: <id>`, and travels with the assert through any edit of its text** — so that a probe's `expect_claim` and an exemption's key stop rotting when `ruff format` reflows a literal or a setting is renamed, **can never be silently re-targeted onto a different assertion** (identity is carried, not inferred from a pattern over neighbours), and **need no second artifact** (no per-PLAN generator, no spec file, no repin cycle) to stay correct. The driver keeps addressing claims **only** by `Claim.stable_key` (PLAN-0115 AC-5 stays as written); what changes is that `stable_key` gains a second, author-declared derivation — `@<id>` for a tagged claim, `owner|source|#occurrence` for an untagged one — under the invariant **one claim, one key**. A `tag` subcommand migrates an existing text-keyed battery and **prints per-battery equivalence values** (`resolved_same=… resolved_differ=0`), never a bare PASS. The three PLAN-0126 story batteries migrate first; when they run green on tags, `tests/batteries/plan_0126_story_generator.py`, `tests/api/test_story_battery_generator.py` and `tests/batteries/s309-story-battery-generator.json` are deleted in the same PR. Four PRs (one contingent on SD-b), one PLAN, no ADR (SD-d).

## 0. Where this PLAN starts — the frontier

**Solved (do not re-do):** the driver addresses claims by an exact key and refuses everything it cannot address **before the first mutation** (`_validate`, `tools/probe_battery/_battery.py:327-344` ✔); the lint moves that refusal to commit time for every committed battery and is `always_run` because the rot is authored on the code side, never the battery side (`tools/probe_battery/_lint.py:14-22` ✔; `tools/check_battery_definitions.py:17-20` ✔); the coverage report names every claim that is neither reddened nor exempted, and calls an addressed-but-absent key STALE (`tools/probe_coverage.py:213-216`, `:226`, `:254-268` ✔); and the s309 interim generator resolves keys from `(owner, source-prefix)` with an exactly-one refusal (`tests/batteries/plan_0126_story_generator.py:113-122` ✔).

**Uncracked (this PLAN's work) — the dispatch's three requirements for an address:**
1. **Survives an assert's text changing.** Today's key *is* the text (`Claim.stable_key = f"{owner}|{source}|#{occurrence}"`, `tools/probe_coverage.py:96` ✔; `source` is the whitespace-normalised first 160 characters of the assert's test expression, `:162` ✔). Change the text, the key addresses nothing. The lint makes that **loud**, but the repair is a hand-typed key per probe, and s287 measured two batteries dead for a whole session before the lint existed (`_lint.py:3-13` ✔ — recorded there; not re-measured).
2. **Never silently re-targets onto a different assertion.** This is hazard **H1**, and it is where the obvious fix fails. A reference resolved from `(owner, prefix)` with exactly-one (the s309 generator's rule, `:115-122` ✔) has this failure: an owner asserts `result.error == "missing"` and `result.error == "missing" or retry`; delete the first, and the prefix `result.error ==` still resolves **exactly once — to the other assertion**. The battery keeps "witnessing" a claim nobody declared. The exact key fails loudly in the same situation. **Any address that is looser than the claim's own identity has this hole, and no rule over the *current* source can close it** — the information that the first assert *used to exist* is not in the current source. §2.4 works this through for every candidate.
3. **Needs no second artifact that can drift from the battery.** The s309 generator is that artifact: it lived outside git across s304–s305, STATUS named a stale copy as the only copy, and that copy produced **35** page probes against the committed **41** (⚠️ asserted-not-verified — s309 prose in the dispatch and in the generator's own docstring `:6-12` ✔ as text; a regeneration from it would have deleted the AC-11 and AC-3 witnesses without a word). The interim guard (`tests/api/test_story_battery_generator.py:42-59` ✔) makes that drift loud; it does not remove the artifact.

**The resolution this PLAN proposes:** requirements 1 and 2 are only jointly satisfiable if the identity is **carried by the assert itself** rather than **derived from its text or its neighbours**. A trailing `# claim: <id>` comment on the assert's anchor line is exactly that: it survives any edit to the text (1), it is deleted **by the same edit that deletes its line** and can be held by no other assert (2), and it lives in the one place that cannot drift from the code because it *is* the code (3). §2 is the design; §2.3 maps it onto H1–H4.

**Eliminated, not automated** (the dispatch permits this): **(E1)** the per-PLAN generator pattern — its only irreducible job was resolving intent to a key, and a tag *is* the intent written where the key is read. **(E2)** the `(owner, prefix)` exactly-one rule, in any form, including as a load-time reference — it is H1's mechanism, not its cure (§2.4). **(E3)** a "repin" subcommand that re-resolves stale text keys from a stored reference — it keeps a second field that must be validated in three places (hazard H2) and defends H1 only procedurally, by a human reading a printed diff (§2.4, direction b'). **(E4)** the interim `--check` guard (`plan_0126_story_generator.py:1008-1027` ✔) — once a key cannot rot, "does the generator agree with its output?" has no object.

**A hazard already present today, recorded so it is not rediscovered:** two untagged claims of one owner that share `(owner, source[:160])` share a text key and are disambiguated by `occurrence` alone — so deleting the first silently re-points `#0` at the second. That is H1 inside today's exact-key scheme, and the collision class is **not** "long asserts only": Code measured it on the real `enumerate_claims` (§1 G29 — ⚠️ measured by Code, session 310, not re-run by the drafter) with two **identical short asserts**, `test_repeats|row is not None|#0` and `#1`, no truncation involved — the very `_REPEATED` shape PLAN-0115 AC-5's own fixture uses (G22, `tests/tools/test_probe_coverage.py:174-180` ✔) — and after deleting the first, the deleted claim's key still resolved (`True`). The 160-character truncation (`tools/probe_coverage.py:162` ✔) is a second way into the same class (also `True` in the same run); two asserts distinct within 160 characters were the control (`False`). The live exposure, counted by Code over all 50 committed batteries (§1 G30 — ⚠️ measured by Code, session 310): **1272** addressed keys (probe `expect_claim` ∪ exemption keys) against 1276 claims enumerated across 52 claim-source modules; **5** colliding `(module, owner, source)` groups holding **11** claims; **11 addressed keys sit in a collision class today** (e.g. `test_a_repeat_warn_at_the_same_fingerprint_is_deduped|run_goal_gate({}) is None|#0`, `#1`, `#2`; `test_both_transports_time_out_in_the_same_window|pytest.raises(gave_up)|#0`, `#1`). Tags close the whole class: a tagged twin is `@<id>` and cannot be re-pointed by a deletion (AC-5); nothing in this PLAN widens the truncation.

## 2. The design — claim tags

### 2.1 The grammar (one form, deliberately narrow)

- A **tag** is a **trailing comment** `# claim: <id>` on the **anchor line** of a claim — the physical line that ends the claim's logical line. For an `assert`, that is the statement's last physical line (its only line when it is one line long; the `) == 1` line of a multi-line one). For a `with pytest.raises(...)` / `pytest.warns(...)` claim, it is the last line of the `with` **header** — the line carrying the header's `:` — never a line of the body. `<id>` matches `[A-Za-z0-9][A-Za-z0-9_./-]*`; it cannot contain `|`, `#` or whitespace, so a tag key can never look like a text key. The form is two spaces then `# claim: <id>` — the spacing `ruff format` itself emits for an inline comment, so a format pass is a no-op on a tag.
- A tagged claim's `stable_key` is **`@<id>`**. An untagged claim's key is unchanged.
- Tags are read from **`tokenize` COMMENT tokens**, never from a regex over raw lines — a `# claim:` inside a string literal or a docstring is a STRING token, not a tag. The anchor line of each claim is the row of the NEWLINE token that ends its logical line (`tokenize` emits NL, not NEWLINE, for the continuation lines of a multi-line statement), so anchor and tag are read from the same token stream. A COMMENT token may hold other comments before the tag (`# noqa: E501  # claim: E1`): the tag is the `# claim:` occurrence inside the token, and a token holding two of them is malformed.
- **Placement is trailing on the anchor line, and nowhere else — for a reason that is in the code, and was measured.** `enumerate_claims` derives `source` by `ast.get_source_segment` over the assert's *test expression* (`tools/probe_coverage.py:155` ✔) or the *context-manager call* (`:171` ✔) — that is, over the node's `(lineno, col_offset)`–`(end_lineno, end_col_offset)` span. A comment after the statement's last token lies **after** that span's end, so it never enters `source`. Code measured this on the real enumerator (§1 G27 — ⚠️ measured by Code, session 310, not re-run by the drafter): a trailing tag on a one-line assert, on the closing line of a multi-line assert, and on a `pytest.raises` header all left `source` unchanged (`leaked = False`), while a tag on an **interior** line of a multi-line assert entered it (`source = 'f( a, # claim: E3 b, ) == 1'`, `leaked = True`). The previous draft's reason for line-above — "a trailing comment would enter `source` and change the text key of that very claim" — was therefore true only for interior lines, and the line-above form it chose has a worse property: it rebuilds H1 (G28, §2.3). **What trailing placement buys** is exactly the property §2.3's H1 argument needs: the tag is removed by the same edit that removes its line — there is no separate comment line that an ordinary delete can leave behind.
  - **Interior lines are prohibited** (kept from the previous draft, now for the measured reason). A `# claim:` on any physical line of a claim's logical line other than its anchor is refused at enumeration: it is inside the sliced span and would change the text key of that very claim — G27's `leaked = True` row is the shape.
  - **The first physical line of a multi-line statement is eliminated, not offered.** The s310 dispatch proposed "first or last"; the drafter declines the first line by mechanism: for the common multi-line shapes — `assert f(  # claim: x` … `) == 1` and `with pytest.raises(  # claim: x` … `):` — the sliced node *starts on that line and continues past it*, so `get_source_segment` includes the comment and `source` leaks exactly as on an interior line. (The parenthesised opener `assert (  # claim: x` happens not to leak, because the `Compare` node starts on the next line — but a Black-compatible formatter keeps a comment after an opening bracket glued to that bracket and will not re-join the statement, so the form fights `ruff format`.) **Code ran that row (G32) and the drafter's reading holds**: both shapes leak, so the first line is eliminated on measurement, not on inference. One anchor per claim also removes any placement choice from §2.5.
- **Refusals at enumeration** (new `ClaimTagError`, a `ValueError` subclass), all three loud at `enumerate_claims`, so the lint (`always_run`) and the driver (before the first mutation) both see them:
  1. **Duplicate id** — the same id on two claims of one module; the message names both lines. Load-bearing, not a nicety: G31 records that Jest and insta reintroduce H1 on a duplicated explicit name and neither validates for it.
  2. **Malformed id** — `# claim:` followed by an empty id, an id containing a character outside the grammar, trailing text that is not a further `#` comment, or a second `# claim:` inside the same COMMENT token.
  3. **Unattached tag** (replaces the previous draft's "orphan") — a `# claim:` comment on a line that is not the anchor line of exactly one claim: a comment-only line (which is what the previous line-above form now is — it is **refused**, not silently left unaddressed, so no author can write the old form by habit and lose the address); an **interior** line of a multi-line claim (reported as interior, naming the claim it sits inside, since it would leak into `source`); a code line that ends no claim; or a line that ends more than one claim (`assert a; assert b  # claim: x` — ambiguous; `ruff format` splits such lines anyway).

  A formatter cannot silently defeat any of these: `ruff format` runs at pre-commit (`.pre-commit-config.yaml:21-26` ✔), and if it ever moved a tag off its anchor line the tag would be unattached and the same commit's `always_run` lint would refuse it — loud, in the commit that did it.

### 2.3 How each dispatch hazard is met

- **H1 — silent re-target (the centre).** The tag sits on the claim's own anchor line, so **no edit can remove the assert and keep its tag**: deleting the statement deletes the line the tag is on, and deleting the assert's text while leaving its comment leaves a `# claim:` on a line that ends no claim, which enumeration refuses as unattached (§2.1). After the deletion in §0's example, `@E1` resolves to **nothing**: `_validate` refuses before the first mutation (`_battery.py:333-339`), the lint refuses at commit (`_lint.py:87-91`), and the sibling `result.error == "missing" or retry` cannot be chosen because it carries a different tag or none. This is a mechanism, not an editing convention — and the distinction was measured: under the line-above form this draft previously specified, Code found (G28 — ⚠️ measured by Code, session 310) that deleting **only** the tagged assert's line leaves `# claim: E1` immediately above the sibling, the old orphan rule does not fire (the next statement *is* a claim), and `@E1` addresses the survivor — H1 rebuilt inside the tag design by an ordinary one-line delete. Trailing placement has no such edit. The refusal is **structural** — no rule over the current source is consulted — and it is inherited from code that already exists; AC-2 witnesses it RED and replays the prefix rule on the same fixture as a closed-incident oracle (the PLAN-0115 AC-6 pattern, `0115:226-231`). Tags also close the exact-duplicate class G29 measured on today's key (two identical short asserts, `#0` re-pointing at the second on deletion): a tagged twin is `@<id>` and the other keeps its `#…` slot (AC-5). **The residual, stated narrowly:** a tag **transplanted by hand** — cut from one anchor line and pasted onto another claim's — makes `@E1` address the other claim, and the driver does **not** reliably catch that. Its classification compares the failure's site with the *declared* claim's file and line (`_outcome.py:470-485` ✔ as text) and credits only `WITNESSED` (`CREDITING_OUTCOMES`, `:96` ✔), so the outcome depends on which assertion the probe's mutation reddens: ⚠️ asserted-not-verified — a specialist read of `_outcome.py:462-492` and `:96`, relayed by the s310 dispatch and **not run by Code** — says a transplant yields `GREEN` (nothing reddens) or `WITNESSED` (the transplanted-to sibling reddens at its own line and is credited — the silent shape), and a `MISFIRE` only when the *original* assert reddens at a line the tag no longer names. The previous draft's claim that a transplant "is caught at run time as a `MISFIRE`" is withdrawn. What does see a transplant is the diff — a `# claim:` moving between lines is visible to the reviewer of that commit (§2.6 R-B) — and nothing mechanical; §9 records the one fixture through the real driver that settles the classification. AC-8's second case still pins the live-lookup path for line shifts *above* a tagged claim.
- **H2 — two address forms coexisting.** There is **one field** (`expect_claim`) and **one lookup** (`stable_key` in the index). A tag key and a text key are two *derivations* of the same key, not two paths, so `_validate`, `_overlaps` and the lint cover both with no new code (§2.2) — AC-2, AC-6 and AC-7 each exercise the tag form through the *unchanged* refusal. What could reintroduce a second path is a reference-shaped field in the JSON; `Probe.from_json` now refuses those (AC-3). The end state SD-f proposes — every *addressed* claim tagged, text-form addresses refused by the lint — collapses even the two derivations to one at the address surface.
- **H3 — exemptions are addressed too.** `Battery.exemptions` keys are `stable_key`s (`_battery.py:233-240`), so an exemption is written as `"@<id>": reason`, the orphan check (`_lint.py:101-112`) reports a deleted tagged claim's exemption exactly as it reports a text one, and the `tag` subcommand migrates exemption keys alongside probe keys (AC-6, AC-9).
- **H4 — the coverage denominator.** `render_report(claims, credited, exemptions, key_of=stable_key)` (`_battery.py:644-646`) is unchanged; the denominator is still *every* claim enumerated from `claim_sources`, tagged or not, and a gap is still a claim in neither map (AC-7). Tags are required only for what a battery **addresses**; the denominator needs none, which is why coexistence costs nothing at the report.

### 2.4 Why each candidate direction loses to tags

- **(a) Reference resolved at load `{owner, prefix}` → key.** Reopens AC-5 directly (a second address form in the API) and has no structural answer to H1: after the deletion, the *only* fact that would refuse the sibling — that the declared assert once existed — is absent from the current source. Every mitigation is a heuristic (edit distance, claim-count deltas) that turns a loud failure into a warning someone must read. **Rejected for H1** (the dispatch's REJECT-if condition, restated in writing).
- **(b) Keep AC-5, repair rot with tooling.** The honest version (call it **b′**, a *lockfile*): each probe carries a pinned text key **and** a `(owner, prefix)` reference; the driver runs on the pin, a `repin` subcommand re-resolves the reference when the pin dies and prints `old → new` for review. H1 is defended, but only **procedurally** — the tool prints the sibling's text and a human must notice it is a different assertion — and the design adds a field that must agree with the pin in `_validate`, the lint and `repin` (H2's surface, three places). Tags defend H1 structurally with zero new refusal code. **Second choice**, offered in SD-a as the fallback if Cray rejects tags.
- **(c) Specs as native driver input.** The generator generalised: an alternate path by construction, and it inherits (a)'s H1 hole because its resolver is the prefix rule. **Rejected.**
- **(d) Status quo plus per-PLAN generators with guards.** Each generator is a second artifact with the s309 drift shape; the guard makes drift loud but every new generated battery adds one more artifact to keep honest. **Rejected** — it scales with the number of generated batteries, which is the dispatch's own objection.

### 2.5 The `tag` subcommand (migration and convenience)

`python -m tools.probe_battery tag <battery.json> [--dry-run]` — for every key the battery addresses (probe `expect_claim`s ∪ exemption keys): resolve it against `claim_sources` to a claim; if that claim's anchor line already carries a tag, **adopt** it; otherwise choose an id (SD-e: default `<battery-stem>/<probe-name>` for the first probe declaring the key, `<battery-stem>/exempt-<k>` for an exemption) and plan **an append** of `  # claim: <id>` to the claim's **anchor line** (§2.1 — the line that ends its logical line; there is no first-vs-last choice, because the anchor is the one line the enumerator reads). **Compute the whole plan first, refuse before writing** (exit 2, nothing touched) if any key is unaddressable, any chosen id is already used in its module, or any anchor line would exceed the project's ruff `line-length` after the append (below). Then apply the plan **in place**: an append changes no line count, so **no line number shifts** and files may be written in any order — the bottom-up ordering the previous draft needed for line insertion is gone with the insertion; each touched file is rewritten once, with every line other than its anchor lines byte-identical. Rewrite every addressed key to `@<id>`, re-enumerate, re-run `lint_battery_file` on the result, and **print** `battery=<name> addressed=<n> tagged=<n> adopted=<m> resolved_same=<n> resolved_differ=0` where `resolved_same` counts keys whose pre-rewrite resolution `(owner, source, occurrence)` equals the post-rewrite `@` key's resolution. A non-zero `resolved_differ` — or a `ClaimTagError` from the post-write enumeration — is a refusal (exit 2) and the files are restored from the in-memory originals. Under trailing placement the equivalence line is also the **leak detector**: a tag that entered `source` (an interior line, or the first-line shape G27 has no row for) would change the post-rewrite `source`, `resolved_differ` would count it, and the tool would refuse and restore — so a leaking tag cannot be committed by the tool. The proof is claim-identity equality, printed as values — with tags every *key string* changes by construction, so "keys_equal" would be meaningless; the dispatch's shape is honoured in substance (per-battery values, never a bare PASS).

**What append introduces, and the rule for each:**

- **An anchor line that already carries a trailing comment** (`# noqa: …`, `# type: ignore[…]`, `# pragma: …`, prose). The tag is appended **after** the existing comment, separated by two spaces, and the existing comment's bytes are preserved in place: `assert x  # noqa: E501  # claim: <id>`. The tag reader finds `# claim:` anywhere in the COMMENT token (§2.1), so order does not affect resolution; the tag goes last so that each pragma parser, which reads rightwards from its own marker, sees exactly what it saw before. That `ruff` and `mypy` tolerate a further `#` comment after their own directive is ⚠️ asserted-not-verified (G31's survey names trailing placement as their convention; co-existence on one line was not measured) — it is exercised for real by the pre-commit `ruff` and `mypy` hooks on the first commit that tags such a line, and AC-9's fourth case pins the ordering and the byte-preservation. An anchor line that already carries a `# claim:` is the adoption case; a line carrying a *different* tag cannot occur under trailing placement (a tag on the anchor line *is* that claim's tag), so the previous draft's "different tag on the line above" refusal has no object and is dropped.
- **Line length.** `ruff` selects `E` with `line-length = 100` (`pyproject.toml:64-70` ✔), so E501 counts an appended tag, and both `ruff --fix` and `ruff-format` run at pre-commit (`.pre-commit-config.yaml:21-26` ✔). The tool reads `[tool.ruff] line-length` from the project's `pyproject.toml` (ruff's default, 88, when absent), measures every planned line, and **refuses in the plan phase** — printing `overlong: <path>:<line> width=<w> limit=<L>` per offending line — rather than write a line the same commit's `ruff` hook would reject or leave `ruff format` to reflow. The remedy is the adoption path: the author tags that claim by hand with a shorter id (or explodes the statement so its anchor line is short) and re-runs `tag`, which prints it under `adopted=`. Why the tool does not let `ruff format` reflow an over-long tagged line for it: a Black-compatible formatter places the trailing comment after the closing bracket of the exploded statement — the new anchor line, still valid — but that placement is ⚠️ asserted-not-verified here, and a tool that depended on it would be writing a tree it cannot lint. (Length interacts with SD-e: `<battery-stem>/<probe-name>` ids run to ~50 characters, so an assert wider than roughly 45 columns overruns at 100; the refusal prints the count so the ruling can be revisited with numbers if Step 3 or SD-b's bulk run hits it often.)
- **Which physical line of a multi-line statement.** The anchor, always — §2.1 eliminates the first line by mechanism. For `assert f(\n    a,\n    b,\n) == 1` that is the `) == 1` line; for an exploded header `with pytest.raises(\n    X,\n):` it is the `):` line. The tool takes the anchor from the same `tokenize` NEWLINE row the enumerator uses, so what it writes is what the enumerator reads.
