## Goal

Make it **structurally impossible** for two `pytest` processes to share one test database, and make the gate's own `check` criteria run against a database **nobody else binds** — so that a `DeadlockDetectedError` on `DROP SCHEMA` or an `UndefinedTableError` can never again be a fabricated defect. Two mechanisms, both ruled: the Stop-hook goal gate injects an **identity marker** (`VERO_TEST_DB_ROLE=gate`) that `tests/db_support.py` turns into a distinct database name (SD-A = (b)); and every pytest session takes a **Postgres session-level advisory lock** keyed on the database name it is about to drop schemas in, held for the session's lifetime, so a second arriver on the same name **errors, naming the holder** (SD-B = (b)). The build's own acceptance bar is set by the opposite failure: **a guard that fails OPEN reports exactly what a working guard reports on a clean run**, so every criterion here carries a positive control, and the session prints the values it measured on clean runs as well as dirty ones.

## 1. The failure this prevents, stated once (the oracle every AC is judged against)

The gate runs `check` criteria at every Stop (`_goal_gate.py:337-345`, each as an argv subprocess at `:302-334`). A `pytest` criterion binds the **per-checkout** test database — `vero_lite_test_<8-hex of repo root>` (`tests/db_support.py:123-134`, applied at import `:151`) — whose teardown is a **`DROP SCHEMA public CASCADE` per test** (`:227`, inside `_reset_public_schema_once` `:213-228`, armed by the autouse fixture `tests/conftest.py:40-51`). A second pytest on the same name — the agent's own run, one of the probe battery's children (`tools/probe_battery/_battery.py:360-385`, one pytest per probe), or a second session in the same checkout — drops the first one's schema mid-run. Measured output (Code, s275; also s228 and s253): `DeadlockDetectedError` on the schema drop plus `UndefinedTableError` on four tables — **failures indistinguishable from real defects**, recorded into an append-only trail (`goal.json` `evaluations[]`) and, under `enforce: true`, ridden straight into the V2-D3 ladder (`_goal_gate.py:684-687` → `_failing_consequence` `:593-613`).

The per-checkout scoping is **correct and stays** (19 live worktree entries; every measured collision was *within* one checkout, between two processes). What is missing is the binding between a *process* and the database it is about to destroy.

## 2. The central risk of THIS build: a guard that silently fails OPEN

A Postgres advisory lock is released the instant its holding backend dies. If the holder is lost — an exception in the holder, a closed event loop, interpreter teardown ordering, a `pg_terminate_backend` from a cleanup script — the guard stops guarding and the next pytest proceeds exactly as today, **with no signal at all**. "No contention reported" is therefore not evidence the guard works; it is also what a dead guard reports. Consequences for this PLAN, binding:

- Every AC carries a **positive control** in the shape `tests/services/db/test_teardown_bound_reddens.py:105-113` (the unconditional-failure control) and `:116-137` (the holder-really-holds control) already ship — clone them, do not invent.
- The session prints a **token carrying measured values** on every run (§4.2.5), never a bare PASS/FAIL (CLAUDE.md §8).
- The **holder's liveness is re-proven at the chokepoint** every DB test (§4.3), so a holder lost mid-session is a distinct, loud outcome, not a clean finish.
- The second arriver **errors** (a reserved exit code), never `pytest.skip` — a mass skip reads as a pass on the summary line, and the floor that catches mass skips (`tests/conftest.py:184-202`) is armed only under `CI=1` with args exactly `["tests"]` (`:190-193`), i.e. never in a gate check.

## 4. Design — the D8 contract made concrete

### 4.1 The marker (SD-A = (b), ruled)

- The gate sets **`VERO_TEST_DB_ROLE=gate`** in the environment of every `check` subprocess (`_run_one_check`, F12) and carries it across the WSL boundary with `env_with_wslenv_passthrough(("VERO_TEST_DB_ROLE",), env)` (F13). Every criterion gets it; only pytest reads it.
- `tests/db_support.py::_isolate_test_database_per_worktree` reads the marker and **suffixes the name it would otherwise resolve**: `vero_lite_test_<8hex>` → `vero_lite_test_<8hex>_gate` (28 chars, inside Postgres' 63). The value is validated `^[a-z0-9_]{1,16}$`; anything else is a loud `RuntimeError` at import (a typo must not silently mean "no isolation"). The role is **free-form by design** — a test that needs a genuinely separate child session sets `VERO_TEST_DB_ROLE=t<pid>` and gets its own database through the same code path the gate uses, so the isolation lever is exercised by the suite, not only by the hook.
- **Composition with an explicit `TEST_DATABASE_URL` (F9) is SD-1.** Recommended: the suffix applies to whichever name resolves — explicit or derived — because a dev box whose `.env` pins `TEST_DATABASE_URL` would otherwise leave the gate un-isolated with no signal; CI (which pins it, `ci.yml:136`) never runs the Stop hook, so CI's `vero_lite_test` is untouched either way.
- `ensure_test_database` creates the suffixed database on first use as it does today (`:178-204`); `_assert_not_dev_db` (`:160-175`) is unchanged and still holds.

### 4.2 The lock (SD-B = (b), ruled)

**4.2.1 Key.** `key = int.from_bytes(sha256(db_name).digest()[:8], "big", signed=True)` — a deterministic `bigint` for `pg_try_advisory_lock(bigint)`; computed in Python so the gate-side tests and the session agree without a Postgres round-trip; printed in the token.

**4.2.2 Placement — SD-2.** Recommended: the lock is taken on the **`postgres` maintenance database** (the connection `ensure_test_database` already opens, F10), keyed by the *target* name. Reasons: (i) the lock then **precedes** `CREATE DATABASE`, so the F10 race becomes unreachable for guarded sessions and its silence can be replaced by a report (§4.6); (ii) the holder never sits on the target, so a `DROP DATABASE vero_lite_test_<stale>` cleanup is not blocked by a live session; (iii) `pg_stat_activity` is cluster-wide, so `foreign_backends` on the target is measurable from the maintenance connection. Under this placement the name-derived key is **load-bearing** (all sessions share the maintenance DB's advisory namespace, F22). The alternative — lock on the target DB with a constant key — is recorded under SD-2.

**4.2.3 Holder residency and death — SD-3 (the place a silent failure will hide).** Recommended: a **dedicated daemon thread running its own `asyncio` loop** with **one raw `asyncpg` connection** (F4 — no sync driver exists) that executes `SELECT pg_try_advisory_lock(:key)` once and then **parks on an `asyncio.Event`**. The guard object exposes only **synchronous, thread-safe** reads (`state`, `holder_pid`, `key`, `db_name`) and one `release()`; nothing on pytest-asyncio's per-test loops ever awaits the holder. Death: `release()` sets the event via `loop.call_soon_threadsafe`, the coroutine runs `pg_advisory_unlock` + `close()`, and the thread is **joined with a 5 s bound**; a missed join is printed as `release=timeout` in the token, never swallowed. An `atexit` fallback calls `release()` again idempotently. The Postgres-side truth is the backstop: the backend dies with the process, so a stuck holder can wedge nothing — the hazard is the *opposite* direction (a holder that died early), which §4.3 catches.

**4.2.4 Acquisition timing — SD-4.** Recommended: **lazy, at the chokepoint** — the first `create_test_engine()` of the session (F18) starts the holder and blocks on a `threading.Event` (bounded, ~one round-trip) for the outcome. Reasons: (i) acquisition and the liveness check live in **one place**, so a live engine without a held guard is impossible by construction; (ii) a session that runs no DB test never opens a Postgres connection — the suite is Postgres-optional today (`:270-272`, `:277-279` skip paths) and stays so; (iii) **nested pytest children that run no DB test never contend with their parent** — the existing battery scenario tests (`tests/tools/test_probe_battery_scenario.py`) spawn real pytest children, and an eager session-start lock would make every one of them a false second arriver. Eager acquisition in a new `pytest_sessionstart` is the alternative (SD-4); either way a **new session hook is added** (F6): under lazy, `pytest_sessionstart` only *initialises* the guard record (no connection), and `pytest_sessionfinish` releases and prints.

**4.2.5 Outcomes and the token.** Four guard outcomes — `ACQUIRED`, `CONTENDED`, `ABSENT` (Postgres unreachable; DB tests skip as today), `LOST` (holder gone mid-session, §4.3). `pytest_sessionfinish` prints **one line on every run**, values not verdicts:

```
TEST-DB-GUARD db=<name> role=<role|-> key=<int64> outcome=<ACQUIRED|CONTENDED|ABSENT|LOST|NOT-NEEDED> holder_pid=<pid|-> foreign_backends=<N> create_race=<0|1> release=<clean|timeout|-> db_tests=<K>
```

`foreign_backends` = `count(*) FROM pg_stat_activity WHERE datname = :target AND pid <> pg_backend_pid()` at acquisition. **Its source is separate from the lock's verdict, deliberately** (the drafter's earlier qualification, carried into the ADR dispatch): the refused `pg_try_advisory_lock` answers *whether*; the count is a point-in-time measurement that can legitimately read **0 under real contention**, because the other session's per-test engines are `NullPool` (F1) and may be between connections at that instant. The token therefore carries **both** `outcome=` and `foreign_backends=`; a reader who sees `CONTENDED holder_pid=12345 foreign_backends=0` has learned something true about NullPool, not a contradiction. `db_tests` is `len(db_support.EXECUTED_DB_TESTS)` (`:93`), the AC-12 population — so the token also says whether the guard was ever *needed*.

**4.2.6 The second arriver.** `pg_try_advisory_lock` returns `false` → the guard queries the holder (`pg_locks WHERE locktype='advisory' AND granted AND (classid,objid) = key` joined to `pg_stat_activity` for `pid`, `application_name`, `backend_start`) and calls **`pytest.exit(reason, returncode=CONTENDED_EXIT)`** where the reason is the token with `outcome=CONTENDED holder_pid=<pid> holder_app=<application_name> holder_since=<backend_start>`. The holder sets `application_name = "vero-pytest-guard pid=<os pid> role=<role>"` on its connection so the name is meaningful. **Never `pytest.skip`** (§2). `CONTENDED_EXIT = 75` (`EX_TEMPFAIL` in `sysexits.h` — "temporary failure, invited to retry"; pytest reserves 0–5 only) — a literal on both sides of the Windows/WSL boundary (the gate cannot import `tests/`), pinned equal by a cross-file test in the F14 shape.

### 4.3 The chokepoint check — how a lost holder becomes LOST, not clean

`create_test_engine`'s reachability probe (`SELECT 1`, `:275-276`) becomes `SELECT count(*) FROM pg_stat_activity WHERE pid = :holder_pid` — **zero extra round-trips**, one per DB test, and it proves two things at once: Postgres is reachable *and* the holder backend still exists. `0` ⇒ `pytest.exit("TEST-DB-GUARD LOST holder_pid=… — the guard stopped guarding; refusing to run unguarded", returncode=CONTENDED_EXIT)` — **SD-5** records the alternative (per-test ERROR, session continues) and why it is rejected: continuing to run ~400 DB tests unguarded is precisely fail-open. `state == ABSENT` with a *reachable* Postgres at the chokepoint is the same LOST family (the guard could not be established but the database can be reached — the one combination that must never pass quietly).

### 4.4 The gate side

- **Env injection** (§4.1) in `_run_one_check`, F12/F13.
- **A new check state `CHECK_CONTENDED = "contended"`** (`_goal_gate.py:149-154` family) keyed on `returncode == CONTENDED_EXIT` at `:334`. It is neither pass nor fail.
- **An explicit branch** in `run_goal_gate` **before** `checks_all_pass` is computed (`:654-655`): any `contended` ⇒ Telegram `db_contended` naming `holder_pid` from the child's stdout token (captured — `capture_output=True` is already there, `:326`) and **`return None`** with **zero residue** in `goal.json` — the F16 precedent, PLAN-0115 SD-2's ruling applied to the same append-only trail. **SD-6** records the annotate-instead alternative. The re-arm is the next Stop; a persistent contention (an orphaned WSL-side pytest, D8-VX-4's territory) produces a ping per Stop naming the pid to reap — loud by design, not a loop (the gate never blocks on it).
- **Consequence for V2-D3:** a contention outcome can no longer enter `_failing_consequence` (`:684-687`), so no enforce block and no `blocked-pending-human` can be fabricated by a resource collision.

### 4.5 The battery — covered as an expected consequence

Battery children are pytest processes with the inherited environment (F15). Under this PLAN each child that reaches `create_test_engine` takes the same guard on the same name as any concurrently-running agent pytest, and **errors** rather than dropping its schema — no battery change is needed for the *protection*. What may need a change is the *report*: a session-level `pytest.exit` before any test yields a junit file with zero testcases (or none), and the classifier's outcome for that shape is **unmeasured** (`SETUP/COLLECT-ERROR` at `_outcome.py:67` vs `NO-TESTS`, README `:103-105`) — Step 0 measures it; if the shape lands on `NO-TESTS`, Step 6 has the runner (which holds `proc.returncode`, `_battery.py:379-386`) report `SETUP/COLLECT-ERROR` with the token as the named cause (ADR-0038 C6). Either outcome is non-crediting, so a false `WITNESSED` is impossible even before Step 6.

### 4.6 The race silence (F10) — in scope

Under SD-2 = maintenance-DB placement the `CREATE DATABASE` race is unreachable for guarded sessions; the `except ProgrammingError: pass` becomes a **re-check that reports**: re-query `pg_database`; if the row now exists, count it (`create_race=1` in the token, printed, never swallowed); if it does not, re-raise — a `ProgrammingError` that was *not* a race must not be absorbed into a skip.

## Out of Scope

- ❌ **Changing the per-checkout DB scoping** (`db_support.py:123-151`). Load-bearing and correct — 19 live worktree entries; every measured collision was within one checkout, between two processes. This PLAN adds a *process* binding on top of it; it does not touch the derivation.
- ❌ **The lease-file mechanism** for SD-B. Considered and **ruled against** (Cray, s275): a file needs its own staleness protocol and a clock the WSL2 host does not reliably provide (`_lock.py:15-18`; `_goal_gate.py:211-217`), and it cannot know a holder died. The advisory lock is released by Postgres on backend death — the property that makes §4.3's liveness check possible at all. Do not re-propose.
- ❌ **Full-`TEST_DATABASE_URL` injection** for SD-A. Considered and **ruled against** (Cray, s275): it would bypass `_isolate_test_database_per_worktree`'s derivation (F9) and hard-code host/port/credentials into the gate; the marker composes with the existing derivation instead of replacing it. Do not re-propose.
- ❌ **D8-VX-4** — whether the harness's 180 s hook timeout kills the whole process tree or only the hook, i.e. whether the WSL-side pytest child is orphaned holding the `_gate` database. Unmeasured; shapes a follow-on (reaping), not this build. This PLAN's design *tolerates* it: an orphan holding the guard makes the next gate check `CONTENDED` (stand-down + Telegram naming the pid), never a fabricated FAIL.
- ❌ **SD-C and SD-D of the D8 amendment** — remain open in the ADR (⚠️ F21; their content is not readable in the working tree and is not restated here).
- ❌ **`pytest-xdist`** (F5 — absent). If it ever lands, workers are separate processes and must each carry a role; a guard that sees `PYTEST_XDIST_WORKER` set **errors at import** until that is designed, rather than guessing. One line, recorded here so the future failure is loud.
- ❌ **Non-pytest clients of the test database** (`alembic upgrade head` subprocesses a test spawns, ad-hoc `tools/` scripts). The measured collisions were all pytest-vs-pytest; a subprocess a test spawns is that test's own child and inside its guard.

### SD-1 — Does the role suffix apply when `TEST_DATABASE_URL` is explicit?
**RULING (Cray, typed, 2026-09-03, s275): (a) — always suffix, explicit or derived.** Verbatim: "เคาะ SD ทั้งหก เอา (a) หมด". Consequence accepted: "honoured verbatim" at `db_support.py:146` stops being strictly true for the name, which is a contract change on a knob Cray sets by hand — ruled with that stated. CI is unaffected (it pins the URL but never runs the Stop hook).
**Options.** (a) **Always** — suffix whichever name resolves, explicit or derived. (b) **Derived-only** — an explicit URL is honoured verbatim as today (`db_support.py:146`), and the marker is ignored.
**Recommendation: (a).** The failure is per-checkout contention; a dev box whose `.env` pins `TEST_DATABASE_URL` would under (b) run the gate against the *same* database as the agent with no signal — the exact silent geometry §2 forbids. CI pins the URL (`ci.yml:136`) but never runs the Stop hook, so CI is unaffected under (a). AC-1's `-c` child would also fail on such a box under (b), which is how (b) would be *detected* — by a red test, not by design.
**Why Cray's:** (a) changes the meaning of an explicit setting ("verbatim" stops being strictly true), which is a contract change on a knob Cray sets by hand on his boxes.

### SD-2 — Where the advisory lock is taken
**RULING (Cray, typed, 2026-09-03, s275): (a) — on the `postgres` maintenance DB, keyed by the target name.** The F10 creation race is closed by ordering the lock before `CREATE DATABASE`, and the holder stays off the target so stale-DB cleanup is not blocked. The counter's open item stands as a verify-at-execution: a non-superuser role must still be able to `pg_terminate_backend` its own backends for AC-5 — same-role signalling, unmeasured here, and AC-5 is what measures it.
**Options.** (a) On the **`postgres` maintenance DB**, keyed by the target name (§4.2.2). (b) On the **target test DB** with a constant key.
**Recommendation: (a)** — closes the F10 race by ordering the lock before `CREATE DATABASE`; keeps the holder off the target so stale-DB cleanup is not blocked; makes the name-derived key the ADR asked for actually load-bearing (F22).
**Honest counter:** (b) is one connection fewer to reason about (the holder is on the database it protects) and `foreign_backends` is `current_database()`-local. Under (a) a superuser-less role must still be able to `pg_terminate_backend` its own backends for AC-5 — same-role signalling suffices on Postgres ≥ 9.6, unmeasured here.
**Why Cray's:** it decides what a future reader finds in `pg_locks` when diagnosing a wedge, and whether cleanup scripts can drop stale test databases during a session — operational posture on the dev box, not a correctness question.

### SD-3 — Where the holder lives and how it dies
**RULING (Cray, typed, 2026-09-03, s275): (a) — daemon thread + its own asyncio loop + one raw `asyncpg` connection, released in `pytest_sessionfinish` with a bounded join and an `atexit` fallback.** 🔴 This is the decision the dispatch named as the place a silent failure would hide, and it is ruled with the counter on the record: a holder **subprocess** has cleaner death semantics during interpreter-teardown ordering. What makes (a) safe enough to ship is that the liveness check is **DB-side** (§4.3) and does not depend on the thread at all — so the thread dying silently is still *detected*, which is exactly what AC-5 witnesses. If AC-5 cannot be made to redden on a lost holder, this ruling is the first thing to reopen, not the last.
**Options.** (a) **Daemon thread + own asyncio loop + one raw `asyncpg` connection**, parked on an Event; `release()` in `pytest_sessionfinish` with a bounded join and an `atexit` fallback (§4.2.3). (b) A **holder subprocess** (a tiny Python child that takes the lock and waits on stdin EOF) — dies with the parent by construction, no thread/loop interaction at all. (c) A synchronous driver — **not available** (F4).
**Recommendation: (a).** No new process to spawn and reap per session (the battery already spawns one pytest per probe — a holder child per child doubles the process count); the liveness check (§4.3) is DB-side and does not depend on the thread at all, so the thread's death is detected even if the thread dies silently. The stated hazard — pytest-asyncio's per-test loops versus a second loop in a thread — is avoided by exposing **only synchronous** methods on the guard; nothing awaits across loops.
**Honest counter:** (b) has the cleanest death semantics (stdin EOF on parent exit, including SIGKILL of the parent — a daemon thread's socket also closes on process death, so the difference is only during *interpreter teardown ordering*, which is the case the dispatch named).
**Why Cray's:** this is exactly where the dispatch said a silent failure will hide; the choice trades one process per session against thread/loop teardown ordering, and Cray has asked that such a question be surfaced rather than absorbed.

### SD-4 — When the lock is acquired
**RULING (Cray, typed, 2026-09-03, s275): (a) — lazy, at the first `create_test_engine()`.** Structurally there is no live engine without a held guard, Postgres-optional sessions stay Postgres-free, and nested pytest children that run no DB test never become false second arrivers. Accepted cost: a contention discovered mid-session aborts a partially-run session rather than refusing before the first test.
**Options.** (a) **Lazy** — at the first `create_test_engine()` (§4.2.4). (b) **Eager** — in a new `pytest_sessionstart`, before collection.
**Recommendation: (a).** Acquisition and the liveness check are one place (structurally no live engine without a held guard); Postgres-optional sessions stay Postgres-free; nested pytest children that run no DB test (the existing `test_probe_battery_scenario.py` children) never become false second arrivers. Cost: a contention discovered mid-session aborts a partially-run session (still exit 75, still the token) rather than before the first test.
**Why Cray's:** (b) makes every pytest start — including ~60 battery children and every gate check — touch Postgres, and refuses *before* anything ran, which reads cleaner in a terminal. That is a workflow preference about what a refused run looks like.

### SD-5 — Consequence of a holder lost mid-session
**RULING (Cray, typed, 2026-09-03, s275): (a) — abort the session with `CONTENDED_EXIT` and `outcome=LOST`.** Continuing unguarded is fail-open by definition, and the alternative's ~400 per-test errors each happen *after* that test ran its schema drop. Accepted cost, stated: a transient — a cleanup script terminating one backend — discards the rest of a long run.
